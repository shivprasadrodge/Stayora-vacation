# Build Stayora — An AI-Powered Vacation Rental Marketplace

Act as a senior full-stack software engineer, UI/UX designer, database architect, and software tester. Build a complete, functional, responsive vacation rental marketplace called **Stayora**, inspired by Airbnb, with its own original branding and design.

The goal is to create a working full-stack college project that can be developed within approximately two days and later used for a research paper on personalized property recommendation systems.

**Important:** Do not build only a static UI or landing page. Implement the frontend, backend, database, authentication, property management, booking workflow, and recommendation algorithm. Make reasonable decisions without repeatedly asking me questions.

## 1. Technology stack

Use the following stack:

- Frontend: React with Vite and TypeScript.
- Styling: Tailwind CSS.
- UI components and icons: shadcn/ui and Lucide React where appropriate.
- Backend: Node.js with Express and TypeScript.
- Database: PostgreSQL.
- ORM: Prisma.
- Authentication: secure session-based authentication or an equivalent secure authentication implementation.
- Form validation: Zod.
- Charts: Recharts for the admin dashboard and research metrics.
- Image handling: use reliable external demo image URLs initially; structure the application so image uploads can be added later.
- Testing: Vitest and appropriate API tests.

Use Replit's supported database and deployment facilities. Store secrets in environment variables. Do not hardcode credentials.

Keep the application in one Replit project, with a clear separation between frontend, backend, database schema, and shared types.

If a requested service is unavailable, implement a working alternative and explain the limitation.

## 4. Database design

Create a proper relational PostgreSQL database using Prisma.

Include these entities and relationships:

- User: id, name, email, password hash, role, createdAt.
- Property: id, hostId, title, description, city, country, address, latitude, longitude, pricePerNight, propertyType, maxGuests, bedrooms, bathrooms, amenities, image URLs, average rating, createdAt.
- Booking: id, userId, propertyId, checkIn, checkOut, guests, totalPrice, status, createdAt.
- Review: id, userId, propertyId, bookingId if applicable, rating, comment, createdAt.
- Wishlist: id, userId, propertyId, createdAt.
- UserPreference: id, userId, preferredDestinations, preferredPropertyTypes, preferredAmenities, budgetMin, budgetMax, preferredGuests.

Add appropriate foreign keys, uniqueness constraints, validation, and database indexes.

Prevent overlapping confirmed bookings for the same property and dates. Validate date ranges, guest limits, ownership, and prices on the server. Do not rely only on frontend validation.

Store passwords as secure hashes. Never store plaintext passwords.

## 5. Backend API

Implement REST APIs for:

- Authentication and current-user information.
- Property listing, property details, search, filters, and sorting.
- Property creation, editing, and deletion.
- Booking creation, availability checking, listing, and cancellation.
- Reviews and ratings.
- Wishlist management.
- User preferences.
- Personalized recommendations.
- Admin statistics and authorized management.

Use clear route organization, reusable middleware, centralized error handling, and consistent JSON responses.

Protect private routes with authentication. Apply role-based authorization for hosts and administrators. Validate incoming request data using Zod.

Never trust the user ID, role, price, or ownership supplied by the client. Derive identity from the authenticated session and calculate booking prices on the server.

Use database transactions where needed to avoid inconsistent bookings. Prevent race conditions when multiple users attempt to book the same property.

## 6. Personalized recommendation engine — the core research feature

Implement a transparent, explainable recommendation algorithm. Do not require a paid AI API.

The recommendation system should rank available properties according to a user's preferences.

Inputs:
- Preferred destination.
- Minimum and maximum budget.
- Preferred property type.
- Desired amenities.
- Number of guests.
- Optional user interaction history, such as wishlisted properties and previous bookings.

Create a normalized weighted scoring algorithm, for example:

- Destination match: 30%.
- Budget suitability: 25%.
- Amenity match: 20%.
- Property type match: 15%.
- Guest capacity suitability: 10%.

Normalize the component scores to a value between 0 and 1 and calculate a final score between 0 and 100.

Use documented scoring rules. Apply sensible partial matches where appropriate. For example, a property within the user's budget should score higher than an otherwise similar property that exceeds the budget.

Filter out properties that cannot accommodate the requested guests or are unavailable for the selected dates.

Sort results by recommendation score and return the highest-ranked properties.

Create a dedicated recommendation service, separate from the API route handlers. Return the final score and a short explanation such as:
- Matches your preferred destination.
- Within your budget.
- Includes three of your preferred amenities.
- Suitable for your group size.

If the user has not set preferences, show popular or highly rated properties and clearly label them as general recommendations.

Provide a page or section called "Recommended for you" with an explanation of why each property is recommended.

Include a simple preferences form where users can save or update their preferences.

Do not claim that this is a machine-learning model or a generative AI system. It is a transparent, rule-based personalized recommendation engine.

## 7. Research and evaluation module

The project should support a research paper titled:

"Design and Evaluation of a Preference-Based Property Recommendation System for Vacation Rental Marketplaces."

Create a research dashboard that allows the developer or administrator to compare the recommendation engine against a baseline ranking method.

Baseline:
- Filter by the same basic constraints.
- Rank matching properties by rating or popularity.

Personalized method:
- Rank properties using the weighted preference score.

Evaluate both methods using a reproducible, locally generated test dataset and clearly defined relevance labels.

Calculate and display:
- Precision@5.
- nDCG@5.
- Average recommendation response time in milliseconds.
- Number of evaluated users and properties.

Use correctly defined metrics. For Precision@5, divide the number of relevant properties in the top five by five, or by the number returned if fewer than five are available, and document the convention. For nDCG@5, use a clearly defined relevance scale and the corresponding DCG and ideal DCG calculations.

Allow the administrator to run an evaluation and display the results in tables and charts.

Keep the test data and evaluation procedure reproducible. Clearly distinguish synthetic test data from real user activity. Do not fabricate experimental results or claim that the personalized method outperforms the baseline before measurements are run.

## 9. Booking and pricing logic

- The user selects check-in and check-out dates and the number of guests.
- Check-out must be after check-in.
- The property must support the requested number of guests.
- Check availability on the server.
- Calculate nights from the selected dates.
- Calculate the total from the server-side nightly rate and any explicitly defined fees.

Use a simulated payment status such as "Payment not integrated" or "Demo booking." Do not pretend to process real payments. Do not collect card details.
